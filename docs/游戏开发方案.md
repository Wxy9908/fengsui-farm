## 一、概念定位

### 1.1 游戏概念

**游戏定名：「丰穗小镇」（2026-08-11 定稿）**——镇名即游戏名（世界观见《故事线与人物规划》§2），品牌标志为**金色麦穗徽章**（与游戏内小麦作物图标同源，微信头像/分享卡片/启动图全套物料复用）。命名取向：世界牌而非玩法牌，为后续从小农场扩展为完整小镇玩法预留空间。

种田经营类游戏，玩家可以收获各种各样的食物，然后用他们去做菜，然后再卖掉换取利润，从而实现循环过程。
我希望制作一个真正有游戏性的经营游戏，并不是单纯的数值堆砌，而是有自己特点的，好玩耐玩的游戏。

### 1.2 参考游戏

我玩过 QQ农场（最经典的种田游戏），星露谷物语（最好玩的种田经营游戏），动物森友会（自由度特别高），
波西亚时光，桃源深处有人家，江南百景图，小生活 - 悠闲小镇物语，爆炒江湖等等，

### 1.3 核心乐趣

能种植各种各样的东西，体会用它们做各种各样的菜的惊喜感。

### 1.4 已确认的关键决策（2026-07-20）

| 决策项 | 结论 |
|--------|------|
| 游戏形态 | 可点击场景（场景图 + 热点区域 + UI 面板，无角色控制） |
| 烹饪系统 | 自由组合 + 食谱发现（组合表驱动，"惊喜感"来自探索） |
| 目标平台 | 手机端（微信小游戏为主路径，APK 直发为辅） |
| 进度结构 | 无尽沙盒，收集与解锁驱动 |
| 时间机制 | 现实时间制（下线也生长，需离线结算） |

## 四、范围裁剪

### 4.1 核心循环

种菜（现实时间生长）→ 收获 → 厨房自由组合试验 → 发现食谱 → 做菜 → 售卖换金币 → 买种子/升级 → 解锁更多作物与地块

### 4.2 首发内容量（MVP，全部数据表驱动）

- 作物 12~15 种，分 3 个解锁层级
- 食谱 30~40 道；组合失败产出"黑暗料理"（也进图鉴，降低挫败感、增加收集欲）
- 4 条升级线：田地、厨房、店铺、便利（目前开放一键收获，更多档位随后续内容叠加）
- 农场等级系统：经验等级门控内容解锁，与金币升级线构成"等级给资格、金币做支付"双轨制（详见 `docs/数据表设计.md` §8）
- 系统清单：种植/收获、厨房组合、食谱图鉴、售卖与经济、升级线、农场等级、离线收益结算（设上限）、每日轻量奖励（手动领取）、化肥催熟（金币换时间）、今日特价（每日一道菜品收购价上浮）、本地存档

### 4.3 首版明确不做（MVP 边界；后续里程碑可开）

角色捏脸换装、钓鱼/采矿等副玩法、装修系统、多人联机、云存档。  
> **修订**：原写「NPC 剧情」——已由 M5 承接（求购/引导/好感）；首版灰盒不做剧情的旧表述作废。独立任务板仍不做（停车场）。

## 五、技术选型

### 5.1 选型结论

- **引擎**：Cocos Creator **3.8.8**（英文界面）+ TypeScript（前端技能直接复用，原生支持微信小游戏一键发布，同一工程可出小游戏/Android APK/网页版）
- **架构**：数据驱动（JSON 配置表定义作物/食谱/升级），单场景 + UI 层级，核心逻辑与表现分离
- **美术**：现行游戏内多为程序化矢量（`art-lib` / `bg-lib`）；**v1.3 起静态资产走 AI（ComfyUI）升级路径**——风格与验收见 `docs/美术风格规范.md`，操作与提示词见 `docs/ComfyUI出图管线.md`。矢量管线可保留为线稿底或过渡，不要求一夜全换。
- **音乐音效**：音效与主 BGM 均为程序化合成（`sim/gen-audio.js` / `gen-bgm.js`）；素材库选品保留为不满意时的退路
- **存档**：本地存档先行，云存档后置到上线后

### 5.2 微信平台约束（反向约束设计与开发）

- **包体**：主包 ≤4MB，主包+分包总计 ≤30MB。**测试版定案（2026-08-11）**：大图/BGM 走微信**分包**，不强制 CDN；CDN 保留为包体顶满或正式上线后的余量方案（须配域名白名单）。美术资源仍按预算精打压缩。
- **运行环境**：小游戏无 DOM，不可用网页技术栈直接开发，必须走 Cocos 引擎 UI 体系
- **网络**：请求域名需在微信公众平台配置白名单，必须 HTTPS
- **存储**：本地存档使用微信存储 API（Cocos 已封装），存档层设计必须以此为接口
- **开发流程**：M1 起定期用微信开发者工具做真机预览，边开发边验证，禁止"先做完再移植"

### 5.3 个人主体上架合规路径

- 个人主体可注册并上架小游戏；**免费无内购免版号**
- 上架材料：软著（个人可申请，成本低）+《游戏自审自查报告》+ 小游戏备案
- 限制：个人主体不可开通内购支付；广告变现（流量主）可行，有访客量门槛
- 本游戏按"免费、无内购"设计，与"积累作品"目标一致
- 政策可能调整，M4 提审前复核最新规则

## 六、可行性结论与里程碑

### 6.1 结论

**可行**。前提条件：首发内容量锁死在 MVP 范围，内容全部走数据表。

1. 组合表设计工作量 → 表格驱动，M1 先用小样验证组合乐趣

## 七、开发纪律（约束整个开发流程）

### 7.1 核心锚点与设计支柱

**核心一句话**：种出各种各样的东西，自由组合做出各种各样的菜——惊喜感。

**三大设计支柱**（所有功能的审判标准）：

1. 收获的期待感
2. 组合试验的惊喜感
3. 经营成长的积累感

任何功能想法先过审判：**加强支柱 → 做；与支柱无关 → 进灵感停车场；削弱支柱 → 砍。**

### 7.3 里程碑验收标准

- 不横向铺系统，只纵向切：每个里程碑 = 一个可玩的完整循环
- M1 验收：5 分钟能完整玩一遍核心循环
- 每个里程碑结束后自测 30 分钟，记录"哪个瞬间爽、哪个瞬间无聊"；**爽点必须来自核心**（发现新食谱、解锁新作物），否则回头修核心，不堆外围
- **体验双轨（2026-09-29）**：玩法验收通过之外，还须通过 `docs/体验内容开发方向.md` 中**该批次的体验底线**（画面/音乐/人物/故事）；两轨都过才算本批开发完成。风格手法以《美术风格规范》为准，出图操作以 `docs/ComfyUI出图管线.md` 为准，剧情细节以《故事线与人物规划》为准。
- 组合表的乐趣先在纸面/表格上验证，纸面不成立则不动笔写代码

### 7.4 节奏与决策留痕

- 每周 10h，固定节奏优先于突击；每周留半小时回顾：本周工作离核心更近了吗
- 同一问题卡住超过两周 → 降范围，不硬扛
- 任何方向修改，先写入"大事记"（为什么改、改了什么，里程碑级一句话；过程细节追加到 `docs/开发日志.md`），再动手——一个月后回看可识别是否在原地打转

### 7.5 文档纪律

文档真源、反打架规则、改完同步检查单 → **`docs/文档体系.md`**（唯一）。  
禁止在故事线/体验文档里另维护一份「批次 ✅ 状态」与本文 §6 打架。
